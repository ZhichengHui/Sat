## Findings: Review findings on the CDCL of #45 (review #48)

Line numbers are those of `main` at f51c14a. These are reported, not fixed, so they do not conflict with PR #51. The new tests in `core/tests/cdcl.rs` (from #48) call `sat::cdcl` directly. They also pass on PR #51 merged with #48 (8/8, and no instance falls back).

**Rust, `core/src/lib.rs`**
- `:687-701` `certify` → `force_trail` (`:660-680`) runs `reason_ok` on **every** trail variable and scans each variable's whole reason clause. So each conflict costs O(Σ reason length over the trail), while analysis costs only O(seen variables). `mark` (`:617`) also allocates `vec![false; n]` on every conflict. Variables at levels 1 … (lowest level of `learnt`) − 1 are normally not marked. Each such level depends on its unmarked decision, and level-0 propagation finishes before the first decision. So skipping those levels should almost never change the result. Count the marks they receive before relying on this. Level 0 must still be scanned, because conflict clauses can contain level-0 literals. Its marks only grow, so they could be cached across conflicts. Soundness is unaffected because `force_trail` only adds justified marks. PR #51's profile puts `certify` under 5%, so this is an optimisation candidate, not a bottleneck.
- `:542-554` `pick` scans every variable on every decision (O(n) per decision). This is the only O(n)-per-step loop on the search path. A binary heap (or at least an index of the last pick) would remove it. With n=405 (hole9) it is cheap per call, but it is called ~10^5 times.
- `:469-477` `copy_learnt` copies `Search.learnt` into a fresh vector on every conflict. Moving it out (`std::mem::take`) would be free, if the uRust subset allows it.
- `:512` the checks `counter != 0 || p >= self.assign.len() || self.learnt.len() == 0` after the loop cannot fail: the loop breaks only with `counter == 0`, `p` was checked at `:502`, and `learnt` starts with a placeholder. The same holds for the final `i >= len` returns of `all_false` (`:613`), `reason_ok` (`:655`), `satisfies` (`:737`). These are presumably there for the proof, which is fine, but a comment saying so would prevent someone from "cleaning them up".
- Fuel: the `steps < NONE` bound (`:781`) and `restart_at` (geometric ×1.5, capped at `BIG`) are never reached on the suite. On `Sat-2026-11-18` the only instance that `cdcl` does not finish is hole9, which hits the bench's time limit and not a fuel bound. No fallback happens on the 500 random formulas of the tests either.
